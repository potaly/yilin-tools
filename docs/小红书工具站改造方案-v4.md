# 小红书工具站改造方案 v4.1 — 定稿（含代码核查修订）

- 版本：v4.1（2026-10-30）
- 性质：**合并定稿**。取代 v1 / v2 / v3，三份旧文档保留作为论证过程，不再更新
- 来源：v3 的信任与口径纪律 + v2 的执行节奏与频次论证 + v1 的边界约束
- 原则：**这是最后一份方案文档。** 下一步是改代码，不是出 v5

## v4.1 对 v4 的修订

v4 里有两处关于仓库现状的描述是错的，经代码核查后更正。两处都改变了排期：

| v4 的说法 | 实际 | 影响 |
|---|---|---|
| 「`lib/account/store.ts` 已按分档价逐次记录真实成本，后台能看」 | **只有 `app/api/ai-format/route.ts` 调了 `recordUsage()`。** humanize / xhs-copy / xhs-topics 三个工具一行成本都没记 | 成本表**不存在**。阶段 0 半天出不来，要先补记录再等数据（§3） |
| 「`scanDoc` + `analyze` 是纯函数，搬到前端即可」 | **已经在前端跑了。** `Humanize.tsx` 第 86–87 行 debounced `useMemo` 实时调 `scanDoc()`，第 40 行调 `analyze()` | 不存在「拆分」工作。合并检查入口是**界面与信息架构**工作，不是后端改造（§5） |

其余修订：首页主入口的依据改写为待验证假设并给出防自欺的度量口径（§4）；发布后清单删掉「首评埋关键词」和「回复前 5 条」（§2.3）；决策时点改为复盘点并补样本不足的处理（§6）；无数据来源的现状描述改为条件句（§0）。

## 0. 为什么要有这一份

v1 回答了「哪些不能做」，v3 回答了「哪些话不能说」，两份都对，但执行完之后产品不会有人用。v2 回答了「第一周改哪一行」，但在成本和代码现状上说了没核实的话——v4 继承了其中两条，v4.1 已更正。

**三份文档的阶段 0 和阶段 1 都在反复打磨「先核对、先验证、先测试」。累计主张的验证时间，已经超过了直接把阶段 1 做一遍的时间。**

至于站上现在有多少人：**没有数据来源。** 埋点（`lib/analytics/`）是 2026-10-28 提交的，到今天两天；三个小红书工具没有任何用量记录（见上表）。所以现在**无法说出日活**。

- 如果阶段 0 读出来日活确实很小，那么「再精确的流程设计都不如上线一个东西看有没有人用」成立，本文档的节奏适用；
- 如果读出来已经有可观流量，那么阶段 1 的决策时点可以提前，样本门槛也更容易达到。

**先读数，再决定节奏。** 不要拿一个没核实的流量判断去支撑排期。

所以 v4.1 的结构是：**口径从严（v3），节奏从快（v2），范围从窄（v1），现状从实（代码核查）。**

## 2. 口径与边界（从严，先定死）

这一节的约束高于后面所有排期。**先定口径再写界面。**

### 2.1 断言三档

| 档 | 判据 | 界面写法 | 维护 |
|---|---|---|---|
| **平台规则** | 有官方公开文档，能贴链接 | 直接陈述 + 链接 + 核对日期 | 规则变更后更新；记录适用范围 |
| **行业经验** | 运营中广泛可见，但平台未公开确认 | 「经验：…」+ 适用场景 + 限制 | 不得写成算法事实；要能说出观察依据 |
| **本工具假设** | 模型生成或代码推算 | 「这是假设」+ 给出用户可执行的验证方法 | 不得用百分比或权重伪装成数据 |

**第二档必须存在。** 没有它，工具只剩免责声明和官方链接，而经验法则恰恰是这个工具的主要价值。

逐条处理现有断言：

| 现有表述 | 处理 |
|---|---|
| 「核心关键词必须落在标题前 6 个字」 | 降为**行业经验**，改成「核心词靠前，读者扫一眼就能看到」——讲可读性，不讲权重 |
| 「搜索权重最高」 | **删除**。无来源，且是算法断言 |
| 「评论权重高于点赞」 | **删除**。民间说法，无出处 |
| 「限流」类判断 | 改为「这个词建议人工核实」，不预测平台处置 |

### 2.2 检查结果怎么说

分四组展示，**不合成分数**：

1. **文字表达提示** — AI 味规则命中句及解释
2. **需人工核实的用词** — 词表命中；注明是词表提示，不等于平台判违规
3. **格式与长度** — 确定性计算，写明本工具采用的口径
4. **编辑建议** — 仅在用户主动点击后调 AI，展示原文与建议稿差异

顶部给**计数**而不是分数：`3 处建议核实 · 2 处表达提示`。计数是事实陈述，分数是评价——评价会被当成通行证。

**界面禁用措辞表**（写进组件注释，防止以后被改回去）：

| 不能说 | 改说 |
|---|---|
| 发出去会怎么样 / 能不能过审 | 看看有哪些地方要核实 |
| 安全 / 零风险 / 不会限流 | 未命中词表 / 建议人工核实 |
| 检测到 AI 生成 | 这几句读起来像模板 |
| 体检（隐含「查完就没事」） | 检查 |
| 必然 / 一定 / 保证涨粉 | 一律删除 |

### 2.3 发布后清单：只留对读者有用的

v4 保留了「首评埋关键词」和「回复前 5 条评论」，**这两条 v4.1 删除**。

理由：「埋关键词」的目的是影响分发，不是帮读者；「前 5 条」是一个机械配额，它暗示的是数量能换推流，而不是回答谁的问题有价值。两者都不符合「对读者有实际帮助」这个标准。

**保留下来的四条，每一条都要能说清它帮了读者什么：**

| 动作 | 对读者的实际帮助 | 档位 |
|---|---|---|
| 发布后标题和封面仍可编辑 | 标题有错字或读不通时能改掉 | 平台功能（**落地前先在 app 确认仍然存在**，不成立就删） |
| 正文放不下的具体信息（型号、用量、来源、尺码）可以补在第一条评论 | 读者最想知道的细节不会丢 | 行业经验 |
| 有人问了具体问题，就回答他 | 直接解决提问者的困惑 | 常识，不需要理由 |
| 把评论里反复出现的问题记下来，作为下一篇选题 | 下一篇写的是真实有人问的东西 | 行业经验 |

**清单里不出现任何数量、计时或分发相关的表述**——没有「前 5 条」，没有「30 分钟内」，没有「提升推荐」。

### 2.4 隐私与草稿

- 规则检查**不上传正文**（目前确实如此，`scanDoc` / `analyze` 在浏览器里跑），在检查区就近说明
- AI 改写**会把所需文本发到 AI 服务端**，在按钮旁说明，不只放页脚
- 本地草稿：首次保存时说明存在当前浏览器、显示最近保存时间、提供「继续上次 / 清空 / 关闭自动保存」、设保留期限
- 草稿恢复**不自动填入**：顶部显示一行，点了才填。既不覆盖新输入，也不需要弹窗打断

## 3. 成本与额度

### 3.1 成本表现在不存在，要先把它造出来

**核查结果**：`recordUsage()` 只有 `app/api/ai-format/route.ts`（长文图卡的 AI 排版）在调用。`humanize`、`xhs-copy`、`xhs-topics` 三个路由**没有任何成本或 token 记录**。后台能看到的成本只覆盖长文图卡。

所以 v4 写的「阶段 0 半天读出成本表」不成立。实际要分两步：

**第一步（阶段 0，约半天工程量）**：给三个路由补上成本记录。
- 三个路由都已经从 `chatJSON()` 拿到了 usage，缺的是落库那一行
- 复用现有的 `recordUsage()` 和 `lib/account/credits.ts` 的分档价，不要新造一套
- 按工具分字段，否则混在一起看不出哪个贵
- 这一步**不改变任何用户可见行为**，可以独立上线

**第二步（上线后 7–10 天）**：攒够数据再出表。

报表口径：

- 每日 AI 总成本
- 分工具的成本与成功完成数
- **每次被采用结果的成本**（成功生成后真的被复制/保存/继续编辑的那些）
- 失败重试与异常流量占比

第三项是关键。一次生成几厘不重要；十次生成才有一次被复制走，那就是十倍。

> 注意：在第二步拿到数之前，**任何关于「成本可控」或「一次几厘」的说法都没有依据**，包括 v2 写过的那句。

### 3.2 额度

- **规则检查不调 AI、不扣额度、不要登录**——这一条**现在就已经成立**（见 §5），不需要任何前置改造
- **AI 额度暂不调整**，等 §3.1 第二步的数出来
- 调整时三个数一起看：完成率、采用率、单次有效成本。只看生成次数会调错方向
- 长文图卡的 AI 排版走 credits/ratelimit 另一套。**先统一报表口径**，确认必要后再统一产品规则

## 4. 首页与核心路径

### 4.1 首页：粘贴框为主，次级入口降权

v2 的单入口太绝对（假设所有人手里都有稿），v3 的「框 + 四张等重卡片」是两个方案的拼接，用户第一反应会是「我该用哪个」。

v4.1 的做法是**保留两类入口，但视觉权重分层**：

```
┌────────────────────────────────────────┐
│  把手上的文字，整理成能发的小红书内容      │
│                                        │
│  ┌──────────────────────────────────┐  │
│  │ 粘贴草稿、素材，或 AI 写完的初稿    │  │
│  │                                  │  │
│  └──────────────────────────────────┘  │
│  [ 看看有哪些地方要改 ]                  │
│  不上传你的文字；要 AI 改写时才会发送     │
│                                        │
│  还没想好写什么？找选题 →                │
│  要把长文排成图卡？→                     │
└────────────────────────────────────────┘
```

- **次级入口收成小字链接，不做等重卡片。** 有层级才算做了决策
- **主按钮文案用结果，不用机制。** v3 的「先做本地检查」是开发者视角——用户不关心它跑在哪

粘贴**不自动触发 AI**。本地检查先出结果，用户主动点才调 AI。

### 4.2 为什么先试这个入口（以及它可能是错的）

v4 把「发之前检查一遍文字 = 每篇必做」当成既定事实来支撑首页决策。**这是一个假设，没有数据。** 它可能错在两头：

- 有的人发之前根本不检查（写完就发）；
- 有的人检查，但用的是自己的眼睛，不觉得需要工具。

即便如此，它仍然是**第一个值得试的入口**，理由不是「它一定对」，而是：

1. **试错成本最低。** 能力已经建好了（§5），这一轮主要是把它放到首页，不是新建功能。假设错了，损失是几天的界面工作，不是一个模块
2. **它是唯一零边际成本的动作。** 规则检查不调 AI，所以即使大量使用也不烧钱——其他入口做错了会一边没留存一边烧钱
3. **可逆。** 证伪后把它降回普通工具页，首页主位让给选题或图卡，不需要回滚任何后端改动

**同时要防一件事：把粘贴率当成产品价值。**

粘贴是一个**输入动作**，不是价值。用户粘进来看了一眼就走，和粘进来之后真的改了文字，是完全不同的两件事，但在埋点里前者更容易涨。所以：

| 指标 | 性质 | 能不能当成功标准 |
|---|---|---|
| 粘贴 / 输入启动 | 漏斗诊断，只说明入口可见 | **不能** |
| 检查完成 | 漏斗诊断 | **不能** |
| 检查后发生改动（改写、复制走、继续编辑） | 接近价值 | 可以，但要配定性反馈 |
| 用户明确说「有帮助」 | 定性 | 可以，要标样本数 |

**写进埋点看板的注释里**：粘贴率只用于判断首页是否看得懂，任何「粘贴率上升 = 产品变好」的推论都是错的。

### 4.3 任务频次（入口选择的依据，同样是假设）

| 任务 | 估计频次 | 成本 | 依据强度 |
|---|---|---|---|
| 发之前检查一遍文字 | 每篇一次 | 规则部分为零 | **假设**，待阶段 1 验证 |
| 把素材写成笔记 | 一周 2–3 次 | 有 | 假设 |
| 这周写什么 | 一周 1 次 | 有 | 假设 |
| 长文排成图卡 | 偶尔 | 有 | 假设 |
| 发完复盘 | 每篇一次，意愿最低 | 零（纯计算） | 假设 |

整张表都是经验估计，没有一行有本站数据支撑。它用来**排第一个试什么**，不用来论证「所以这个一定对」。

### 4.4 主路径

```
粘贴 / 从次级入口进
  → 本地检查，分四组出结果
  → 用户决定下一步（可以什么都不做就走）
  → 可选：AI 改写 / 带入文案 / 带入图卡
  → 复制或导出
  → 可选：存草稿 / 发布后清单
```

任一步可跳过。**不把「检查完必须改写」做成默认路径。**

## 5. 现状核查：检查能力已经在前端跑了

v4 写了「把 `scanDoc` + `analyze` 搬到前端」，**这是错的——它们已经在前端**：

```
app/tools/humanize/Humanize.tsx
  第 6 行   import { analyze } from '@/lib/aiwei/engine'
  第 10 行  import { scanDoc } from '@/lib/xhs/scan'
  第 40 行  analyze(text).findings.map(...)        9 条 AI 味规则
  第 86 行  useMemo(() => scanDoc(title, body))    词表 + 字数/标签额度，debounced
```

也就是说**「发布前检查」的能力基本已经存在**：词表、AI 味规则、字数标签统计三样都在浏览器里实时跑，零成本、不扣额度、不要登录、断网可用。服务端的 `humanize` 路由另外再扫一遍，那是对前端输入的兜底校验，正确，保留。

所以这一轮的真实工作**不是后端拆分，是界面与信息架构**：

1. **消重**：`ai-flavor` 页面和 `Humanize.tsx` 调的是同一个 `analyze()`。两个入口、一套规则，拆散了用户心智也拆散了流量
2. **重组结果区**：现在是一个列表，要改成 §2.2 的四分组 + 顶部计数
3. **把改写降为可选分支**：现在 `humanize` 的主按钮直接走 AI。要改成「检查结果先出，改写是其中一个按钮」——这一步同时降低了 AI 调用量
4. **换入口位置**：首页主位（§4.1）
5. **落口径**：§2.1 的断言处理和 §2.2 的禁用措辞表

工程量集中在 `Humanize.tsx`、`ai-flavor` 页面和首页三处，**不动 `lib/`**。

## 6. 分阶段与复盘点

v2 的 40% 是武断数字，v3 的「有足够反馈指出重复出现的需求」是没有判据的判据。v4.1 的做法：**日期是复盘点，不是结论点。样本不足时，复盘的结论就是「继续观察」，不是硬凑一个判断。**

### 阶段 0 — 约一天

1. 确认埋点在写入、匿名访客集合可用，**读出当前真实日活与各工具使用分布**
2. 确认 Redis / AI 配置、线上与仓库额度规则一致
3. **给三个路由补成本记录**（§3.1 第一步）
4. 用真机过一遍现有核心路径，列出阻断点

产出一页基线记录。**这一步只装仪表，不出结论**——成本数据要等 7–10 天。

如果第 1 项读出来流量已经可观，回到 §0 调整后续节奏。

### 阶段 1 — 1–2 周：入口、口径、移动端

1. **合并检查入口**（§5 的五项，界面工作）
2. **首页改版**（§4.1）
3. **落 §2 的全部口径**：三档分级、禁用措辞表、隐私就近说明
4. **移动端验收**（本阶段硬性条件，不是优化项）：真机走完打开 → 粘贴 → 定位结果 → 主动改写 → 编辑 → 复制 → 带入图卡 → 导出；键盘不遮挡、无横向溢出、复制失败有回退
5. **埋点补**：`input_started` / `check_done` / `rewrite_requested` / `handoff` / `feedback`，均不采正文
6. **额度不动**，等成本数

**不新增任何 AI 调用**；第 3 项还会减少 AI 调用。

### 第 14 天复盘点

**先看分母够不够。**

| 口径 | 分子 | 分母 | 观察动作 |
|---|---|---|---|
| ① 检查启动规模 | 触发 `check_done` 的独立 vid 数 | 无（绝对值） | 读数 |
| ② 检查后是否发生改动 | ①中又触发 `rewrite_requested` 或 `take` 的 vid 数 | ① 的 vid 数 | 读比例 |
| ③ 用户怎么说 | 反馈为「有帮助」的人数 | 提交反馈的人数 | 读数 + 读开放文本 |
| ④ 任务测试 | — | — | 找 5 个真实创作者各做一次完整任务，记录卡在哪 |

**处理规则：**

- **① < 30 人** → 比例一律不读（分母太小，②③ 的百分比没有意义）。复盘结论是「继续观察」，同时**必须做 ④**，并把注意力转向 §7 获客。日期到了不等于必须下判断
- **① ≥ 30 人** → 读 ② 和 ③，和 ④ 的定性发现一起看。三者方向一致 → 进阶段 2；方向分歧 → 再等两周，期间不改方向
- **连续两个复盘点 ① 都 < 30** → 问题不在产品形态，在没有人来。停止产品迭代，全部资源转 §7，不要继续改界面

**不设通过线。** 没有任何一个百分比能单独决定去留。

### 阶段 2 — 2–3 周：回访

1. **本地草稿续上**（§2.4 的全部可控要求）
2. **串起上下文**：检查 → 改写 → 图卡 → 复制，中间不丢。修掉 `handoff.ts` 现在用 sessionStorage 刷新即丢的问题
3. **发布后清单上线**——纯静态、零输入，内容严格按 §2.3 的四条
4. 同期做 5 个用户的访谈，**只问复盘数据的可取得性和记录意愿**（表单该不该做），不问清单

### 第 21 天复盘点

| 口径 | 分子 | 分母 | 观察动作 |
|---|---|---|---|
| ⑤ 发布后是否回来 | 打开清单页的独立 vid 数 | 无（绝对值） | 读数 |
| ⑥ 草稿是否被用 | 触发 `draft_resumed` 的 vid 数 | 触发 `draft_saved` 的 vid 数 | 读比例 |
| ⑦ 交接是否通 | 完成 `handoff` 后仍有 `take` 的 vid 数 | `handoff` 的 vid 数 | 读比例 |
| ⑧ 访谈 | — | 5 人 | 复盘数据拿不拿得到、愿不愿记 |

**处理规则：**

- **⑤ 与 ⑥ 的分母 < 30** → 不读比例，只读绝对值和访谈。结论「继续观察」，不据此砍功能
- **分母够** → ⑤ 接近零 → 停掉复盘方向，不做表单；⑥ 很低 → 关掉默认自动保存；⑦ 很低 → 先修交接摩擦，不推「工作区」概念
- **⑧ 的结论独立于前三项**：访谈说拿不到数据或不愿记，就改成可下载模板，哪怕 ⑤ 还不错

### 阶段 3 — 由阶段 2 决定

数据回填（六个字段全可选）+ 四段漏斗诊断（纯计算，不调 AI）：

- CTR 低 → 封面和标题
- CTR 高、互动低 → 正文没接住
- 互动高、不涨粉 → 主页和人设

每个百分比必须显示分母和样本量。输出用「观察 / 可能解释 / 下一次可验证的调整」，**是实验建议，不是算法结论**。

### 阶段 4 — 远期

胜率表需要同一用户 15 篇以上数据。收费讨论在这之后。**在此之前站内不出现任何付费入口，包括「即将推出」。**

## 7. 获客：不推迟到阶段 3

零流量的站打磨两个月没人来看，这个风险必须正视。而且按 §6 的规则，**样本不足时获客的优先级会自动高于产品迭代**。

**与阶段 1 并行启动**：

1. 自己运营一个号，内容就是真实创作过程——用自己的工具写、用自己的工具检查。成本为零，而且**自己是重度用户 = 产品问题第一时间暴露**
2. 图卡导出的署名**可关闭**，不默认在用户内容里植入推广
3. SEO 逐页做、逐页验证，不批量造页。见效慢，不是第一个月的主力

记录内容主题 → 访问来源 → 有效完成，**不把曝光当成效**。

## 8. 证伪表与复盘点

| 判断 | 证伪信号 | 什么时候看 | 应对 |
|---|---|---|---|
| 有素材的人需要发布前检查 | ① 很低，且 ④ 访谈无对应痛点 | 第 14 天（分母够才判） | 降回普通工具页，首页主位让给选题/图卡 |
| 检查结果真的有帮助 | ② 很低，③ 多为无帮助 | 第 14 天 | 调规则解释和误报，**不靠增加规则数量解决** |
| 工具间连续流程有价值 | ⑦ 很低 | 第 21 天 | 先修交接摩擦，不强推「工作区」 |
| 本地草稿带来回访 | ⑥ 很低，或访谈显示担心隐私 | 第 21 天 | 关掉默认自动保存，退回仅当前会话交接 |
| 发布后会回来 | ⑤ 接近零 | 第 21 天 | 停掉复盘方向，不做表单 |
| 用户愿意录入数据 | ⑧ 显示拿不到或不愿录 | 第 21 天访谈 | 改为可下载模板 |
| 自营内容能获客 | 有浏览但无有效工具启动 | 阶段 1 起每两周 | 换主题或承接页，不归因于曝光不足 |
| 「检查是值得先试的入口」 | 前两条同时为负 | 第 14 天 | 整条路径重想。**这是最大的单点风险，放第一阶段就是为了最便宜地证伪** |
| **站根本没人来** | 连续两个复盘点 ① < 30 | 第 14 / 21 天 | **停产品迭代，全部转获客** |

## 9. 明确不做

- 不把检查描述成平台审核、限流预测或发布安全保证
- 不伪造热度、搜索量、竞争度、流量权重、爆款概率
- 不把 AI 味命中当作「识别 AI 生成」的真实性判断
- 不在成本数据出来之前调额度，也不说「成本可控」
- 不默认长期保存粘贴正文，不上传规则检查的正文
- 不用小样本的百分比决定成败；分母不够就写「继续观察」
- 不把粘贴率、启动率当成产品价值指标
- 不在发布后清单里出现数量、计时或分发相关的表述
- 不做抓取、自动发布、自动互动、批量运营
- **不碰用户的小红书登录态**
- 不在阶段 4 之前建会员、团队或付费体系
- 不为 SEO 批量生成近似页面
- **不再出第五版方案文档**

## 附：这份方案最可能错的地方

- **「发布前检查是值得先试的入口」是假设，不是数据。** §4.2 已经写明它为什么仍值得先试（成本最低、可逆、零边际成本），以及证伪后怎么退
- **「用户手里已经有东西」没验证过。** 如果来的人多数从零开始，粘贴框会比任务入口更差

- **§2.3 里「发布后可编辑标题封面」需要在 app 里确认。** 不成立就删，理由是功能不存在
- **§2.1 引用的官方文档未逐条核实。** 落地前必须真打开确认适用范围，尤其商业合作报备场景的规则不能推广成普通笔记的统一规则
- **本文档此前两次写错了仓库现状**（成本记录、前端扫描）。任何「仓库里已经有 X」的说法，落地前都要再 grep 一次
