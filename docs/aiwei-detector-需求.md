# AI味检测器 — 需求文档

- 版本：v1.0（2026-10-28）
- 范围：第二个工具「AI味检测」。纯规则引擎，不调 AI。
- 上游：`docs/requirements.md`（站点骨架与扩展约定）、`docs/architecture.md`

---

## 1. 为什么做这个（实现时需要知道，它决定了几个关键取舍）

站点要承接一个小红书账号的搜索流量。那个账号的前 5 篇笔记全部围绕
**「去AI味」**这个搜索词（已实搜验证：前排 5万 / 3.4万 / 1.1万赞）。
读者搜"去AI味"点进来，站上目前只有一个排版工具 —— 导流词和承接物不对口。
这个工具就是补这个口子。

**差异点只有一条，但它决定了整个技术选型：**

> 市面上的"AI味检测"都是把文本丢给模型，让模型自己判断"像不像 AI 写的"。
> 这个工具**把规则写进代码**，不让模型临场判断。

这不是炫技，是产品论点。配套的笔记（`让AI自己判断，一定会漏`）里有硬实证：
规则明明写在文档表格里，模型依然漏掉了"祛湿""补气血""增强免疫力"一整串。
**该写进代码的东西，不要留给临场判断。**

由此直接推出三个决定，实现时不要动摇：

| 决定 | 原因 |
|---|---|
| **检测 100% 纯规则，零 AI 调用** | 产品论点就是这个。顺带：零成本、可单测、结果可复现 |
| **规则引擎跑在客户端** | 零请求、零账单、无需限流。和项目既有的"服务端不碰图"同精神 |
| **不挂登录、不消耗算力** | 冷启动期唯一需要的是试用量，登录是漏斗上的摩擦 |

## 2. 范围

### 本期做

- `lib/aiwei/` 纯 TS 规则引擎：分段分句、9 条规则、加权算分、命中定位
- `app/tools/ai-flavor/` 工具页：粘贴文本 → 体检报告 → 点命中项高亮原文
- 一份可复制的纯文本报告（给用户截图外发用）
- `lib/site.ts` 加注册项
- 每条规则的单测（含反例），放 `tests/`

### 本期不做（YAGNI）

- **AI 改写**。检测能独立上线、零成本、是笔记的实物支撑；改写要调 AI、要算账单、
  要限流，是另一个工程。等检测有了真实使用数据再做
- 批量检测、文件上传、历史记录、导出图片
- 登录门槛、算力扣减
- 自定义规则权重（先用固定权重，有反馈再说）

## 3. 产品设计

### 3.1 核心交互

**不是给一个分数，是指着原文说"这里"。** 分数只是入口，价值在定位。

```
粘贴文本
  ↓
AI味指数 73  ·  命中 6 项
  ↓
命中清单（按严重度排序）
  ├─ 万能结尾 ×1        点一下 → 原文对应位置高亮并滚动到视野
  ├─ 段落长度过于均匀    点一下 → 高亮全部段落 + 显示长度分布
  └─ ...
```

### 3.2 规则清单

**出处标注很重要**：带「锚」的 5 条来自已验证的内容选题，是这个工具的立身之本，
不要删；带「议」的是扩展建议，实现时觉得误报高可以砍掉或降权。

| # | 规则 | 出处 | 怎么判 | 权重 |
|---|---|---|---|---|
| R1 | **排比堆叠** | 锚 | 连续 ≥3 个结构同构短句（长度相近 + 相同句首/句尾模式） | 3 |
| R2 | **"不仅…而且"类句式** | 锚 | 固定句式表：不仅…而且 / 既…又 / 不但…还 / 一方面…另一方面。出现 ≥2 次计命中 | 2 |
| R3 | **万能结尾** | 锚 | 词表：希望对你有帮助 / 让我们一起 / 未来可期 / 值得期待 / 不妨试试 / 相信你也能。**只在最后 2 段内检测** | 3 |
| R4 | **emoji 当装饰** | 锚 | ≥3 个段落以 emoji 开头，或 emoji 数 / 段落数 ≥ 0.8 | 2 |
| R5 | **段落长度过于均匀** | 锚 | 段落数 ≥4 且长度标准差 / 平均长度 < 0.25 | 3 |
| R6 | **信息密度过低** | 议（但有出处，见下） | 每 100 字里数字 + 单位 + 专有名词 < 1 个 | 3 |
| R7 | **关联词密度过高** | 议 | 然而 / 因此 / 此外 / 总之 / 综上所述 / 值得一提的是 / 不难看出，密度 > 每 200 字 2 个 | 2 |
| R8 | **空心词** | 议 | 赋能 / 助力 / 打造 / 全方位 / 深度 / 底层逻辑 / 闭环 / 抓手 / 颗粒度 | 2 |
| R9 | **开场寒暄** | 议 | 在这个…的时代 / 相信很多人都 / 说到…大家都知道。**只在前 2 段检测** | 2 |

**R6 的出处值得单说**，它是整套里最有价值的一条：配套笔记
`AI写的文案一眼假？缺这一层` 的论点就是 —— 别人都在讲"语气像不像人"，
真正缺的那一层是**信息密度**：格式漂亮、分点整齐，读完什么都没拿到。
这条规则是那篇笔记的可执行化，务必实现。

### 3.3 算分

```
score = min(100, round(100 * Σ(命中规则权重) / Σ(全部规则权重)))
```

**把这个公式原样印在页面上**（折叠区里）。别人做黑箱检测器，你公开算法 ——
这和"规则写进代码"是同一个姿态，是差异点的一部分。

分级文案（给用户一句人话，不要只给数字）：

| 分数 | 文案 |
|---|---|
| 0–20 | 基本没有 AI 味 |
| 21–45 | 有一点痕迹，改两处就行 |
| 46–70 | AI 味明显 |
| 71–100 | 一眼就是 AI 写的 |

### 3.4 可复制的报告

结果区底部给一个「复制报告」按钮，产出纯文本，便于截图或贴到别处：

```
AI味指数 73 / 100 —— 一眼就是 AI 写的

命中 6 项：
· 排比堆叠（第 3、4 段）
· 万能结尾（最后一段）
· 段落长度过于均匀（6 段长度几乎一致）
· 信息密度过低（全文 420 字，0 个具体数字）
...

检测规则公开，不调 AI：<站点名> /tools/ai-flavor
```

最后那行署名是导流位。**不要放完整 URL 之外的东西**（不要二维码、不要联系方式）。

## 4. 技术设计

### 4.1 文件落点

严格按 `docs/requirements.md` §3 的扩展约定走，纯逻辑不碰 React：

```
lib/aiwei/
  segment.ts      分段 + 分句（中文标点），纯函数
  rules/
    index.ts      导出 ALL_RULES
    parallel.ts   R1 排比堆叠
    pairs.ts      R2 固定句式
    ending.ts     R3 万能结尾
    emoji.ts      R4 emoji 装饰
    uniform.ts    R5 段落均匀度
    density.ts    R6 信息密度
    connectives.ts R7 关联词
    hollow.ts     R8 空心词
    opening.ts    R9 开场寒暄
  engine.ts       跑全部规则 → Report
  score.ts        权重、算分、分级文案
  report.ts       Report → 纯文本报告

app/tools/ai-flavor/
  page.tsx          服务端壳
  AiFlavorTool.tsx  客户端交互
  ai-flavor.module.css

tests/aiwei-<rule>.test.ts   一条规则一个测试文件
```

一条规则一个文件，是为了让每条都能独立改、独立测、独立砍。
既有 `lib/cards/` 下文件都在 50–270 行，保持同一量级。

### 4.2 接口

```ts
// lib/aiwei/engine.ts
export interface Finding {
  rule: RuleId;
  label: string;        // 给用户看的名字，如「万能结尾」
  severity: 1 | 2 | 3;  // = 权重
  spans: Array<{ start: number; end: number }>;  // 原文字符下标，用于高亮
  detail: string;       // 命中说明，如「6 段长度几乎一致」
  hint: string;         // 怎么改，一句话
}

export interface Report {
  score: number;
  level: 'clean' | 'light' | 'obvious' | 'heavy';
  findings: Finding[];
  stats: {
    charCount: number;
    paraCount: number;
    paraLenCv: number;      // 变异系数
    emojiRate: number;
    numberPer100: number;
  };
}

export interface Rule {
  id: RuleId;
  label: string;
  weight: 1 | 2 | 3;
  detect(text: string, seg: Segmented): Finding | null;
}

export function analyze(text: string): Report;
```

**`spans` 用原文字符下标**，不要用段落序号 —— 高亮需要精确区间。
检测前对输入做一次 `lib/cards/clean.ts` 已有的隐形字符清理
（零宽空格、NBSP 这些会让下标算错），**复用它，不要重写**。

### 4.3 UI 要求

- **手机为主要场景**（沿用 `requirements.md` 的口径）。390×844 下无横向滚动
- 手机上下堆叠：上粘贴区、下报告；`≥900px` 左右双栏
- 原文高亮：报告里点一条 finding → 对应 spans 加底色并滚动到视野。
  再点一次取消。同时只高亮一条，避免花屏
- 粘贴区空态给一句大白话提示 + 一个「填个示例看看」按钮（示例文本放
  `lib/aiwei/sample.ts`，照 `lib/cards/sample.ts` 的做法）
- 深浅色主题跟随全站，不新造配色
- **实时检测，不要"开始检测"按钮**。纯客户端算，debounce 300ms 就够了

## 5. 成功判据

1. **零网络请求**。断网下整个工具正常工作
2. 每条规则有单测，**每条都必须有反例**（见判据 4）
3. 一段典型 AI 生成文案命中 **≥4 条**
4. **一段真人写的口语化文案命中 ≤1 条** ← 这条最重要。
   误报会直接毁掉工具的可信度，宁可漏检不要误报。
   任何一条规则如果让判据 4 过不去，就降权或砍掉它
5. 手机 390×844 无横向滚动，粘贴 2000 字无明显卡顿
6. 点报告里任一条命中项，能在原文里准确高亮到对应位置
7. 不登录可用，不扣算力
8. `pnpm test` 和 `pnpm build` 都通过

## 6. 必须遵守的工程约定

照着仓库现有做法，不要另立一套：

- 包管理 **pnpm**（`pnpm dev` / `pnpm test` / `pnpm build`）
- 测试 **vitest**，放在 `tests/` 平铺，不和源码同目录
- 纯逻辑放 `lib/<domain>/`，**不依赖 React**，可单测
- 加工具 3 步：① `lib/site.ts` 加注册项 ② 建 `app/tools/<slug>/page.tsx`
  ③ 纯逻辑进 `lib/<domain>/` 并补单测。**首页代码零改动**
- 样式用 CSS Module（`*.module.css`），跟现有页面一致
- **不要动 `lib/account/`、`app/login`、`app/admin`、`app/api/*`**。
  这个工具不需要后端
- commit message 用中文、写清做了什么，和现有 git log 风格一致
