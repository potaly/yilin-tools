# 小红书「参考链接 → 仿写 → 生图 → 发布」工作流设计

- 版本：v1.0（2026-10-25）
- 输入：一个基础话题/标题 + 一个仿写参考链接
- 输出：一篇生成好的图文笔记，停在「人工点发布」或全自动发出
- 前置：[04-n8n实操-RSS到Notion.md](04-n8n实操-RSS到Notion.md)

---

## 1. 为什么不能全在 n8n 里做

小红书**没有面向个人创作者的发布 API**，读取笔记详情也没有。所有涉及「以你的身份看页面 / 发内容」的动作，只能由一个**已登录的真实浏览器**完成。

而你的 n8n 跑在 Docker 里，容器里装 Chromium 又重、又容易被风控识别为异常环境。所以架构必须拆成两半：

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  n8n（Docker 容器）          │  HTTP  │  xhs-bridge（跑在你的 Mac）   │
│  ─────────────────          │ ─────► │  ──────────────────          │
│  编排 / AI / Notion / 定时   │        │  Playwright + 已登录的浏览器  │
│  不碰浏览器、不碰 cookie     │ ◄───── │  抓笔记 / 上传图 / 填表单     │
└─────────────────────────────┘        └──────────────────────────────┘
        http://host.docker.internal:8787
```

**已验证**：n8n 容器里 `host.docker.internal` 解析到 `192.168.65.254`，这条路通。宿主机 Playwright 1.64.1、Node v24 都就绪，端口 8787 空闲。

职责切得很干净：**n8n 永远不接触你的登录态**，它只发 JSON；浏览器相关的脏活全在 bridge 里，页面改版只改 bridge 一处。

## 2. 接口契约（先定这个，再写代码）

bridge 监听 `0.0.0.0:8787`（必须，否则容器访问不到），所有请求带 `X-Bridge-Token` 头做鉴权——**不加等于局域网里任何人都能用你的账号发帖**。

| 端点 | 入参 | 出参 | 说明 |
|---|---|---|---|
| `GET /health` | — | `{ok, loggedIn, user}` | 登录态是否还有效，n8n 每次开工先查 |
| `POST /login` | — | `{ok}` | 弹出有头浏览器扫码，登录态存 `user-data-dir` |
| `POST /note/fetch` | `{url}` | 见下 | 抓参考笔记 |
| `POST /note/publish` | `{title, body, topics[], images[], autoConfirm}` | `{ok, status, screenshot, noteUrl?}` | 发布，默认停在确认 |
| `GET /me/notes` | `?days=7` | `[{noteUrl, 曝光, 点赞, 收藏, 评论}]` | 数据回收 |

`/note/fetch` 返回：

```json
{
  "title": "原标题",
  "body": "正文全文",
  "topics": ["#话题1", "#话题2"],
  "imageCount": 6,
  "likes": 12000, "collects": 3400, "comments": 210,
  "publishedAt": "2026-10-20",
  "author": { "nickname": "xxx", "fansLevel": "中部达人" }
}
```

**`autoConfirm` 这个参数是整套设计的安全阀**：默认 `false` —— 图传完、标题正文话题都填好，停在发布页不点最后那个按钮，截图回传给 n8n。你瞄一眼截图，点一下发布。自动化省掉了 95% 的时间，但事故稿发不出去。

## 3. 工作流节点设计

```
Form Trigger（话题 + 参考链接）
  → HTTP: /health  ──登录失效→ 告警并停止
  → HTTP: /note/fetch        抓参考笔记
  → AI#1 爆款拆解（结构化）
  → AI#2 流量诊断（结构化）
  → AI#3 仿写生成（结构化）
  → 查重 Code 节点           和原文重合度 > 30% 打回重写
  → Notion: 写入 status=待确认
  → ⏸ 人审闸门（Wait / 手动触发下半段）
  → 生图分支（文字卡 or AI 图）
  → HTTP: /note/publish      autoConfirm=false
  → Notion: 回写 status=已填充待发 + 截图链接
  → 「7 天后」Schedule → /me/notes → 回填数据
```

### 节点要点

**① Form Trigger**：n8n 自带表单，字段 `topic`（基础话题/标题）、`ref_url`（参考链接）、`image_mode`（文字卡/AI图/混合）。比在 Notion 里新建行更适合调试阶段；跑顺了再换成 Notion Trigger。

**② /health 前置检查**：登录态过期是这条流水线最常见的故障。查不到就走 IF 分支发告警（飞书/邮件），**不要重试**——重试只会让风控更不高兴。

**③ 三个 AI 节点为什么要拆开**：一次让模型「又拆解又诊断又仿写」，三件事都做得稀烂，而且出错了你不知道错在哪一环。拆开之后每一环都能单独 Pin Data 调试。

**④ 查重节点**（必须有）：仿写最大的风险是写着写着变成了洗稿。用一个 Code 节点算仿写稿和原文的字符级重合度，超过 30% 直接打回：

```javascript
const ref = $('note fetch').item.json.body;
const out = $json.body;
const shingles = s => new Set((s.replace(/\s/g,'').match(/.{1,8}/g)||[]));
const a = shingles(ref), b = shingles(out);
const overlap = [...b].filter(x => a.has(x)).length / b.size;
return [{ json: { ...$json, overlap, pass: overlap < 0.3 } }];
```

**⑤ 人审闸门**：用 n8n 的 Wait 节点（webhook 模式）或者干脆拆成两条工作流——上半段生成完写 Notion，下半段由你在 Notion 里把 status 改成「批准」后定时扫描触发。后者更简单，也更符合实际操作习惯。

## 4. 四个提示词

### AI#1 爆款拆解（输出结构化 JSON）

```
下面是一篇小红书笔记的全文、话题和互动数据。请做客观拆解，不要评价好坏。

输出 JSON：
{
  "hook_type": "身份共鸣|反常识|数字清单|踩坑警告|情绪宣泄|教程干货",
  "hook_sentence": "原文第一句，照抄",
  "title_pattern": "把标题抽象成可套用的句式，用 <> 标出可替换部分",
  "structure": ["按段落列出骨架，每项不超过 10 字"],
  "info_density": "每百字信息点个数，估算",
  "topic_strategy": {"大词": [], "中词": [], "长尾": []},
  "cover_style": "首图文案风格描述",
  "cta": "结尾引导方式",
  "personal_brand_dependency": "高|中|低"
}

最后一项很重要：如果这篇的爆点高度依赖作者的个人经历、长相、粉丝基础，
标为「高」，表示这篇不适合仿写。

笔记：<fetch 结果>
```

### AI#2 流量诊断

```
基于上面的拆解，回答三个问题，输出 JSON：
{
  "why_it_worked": ["3 条，每条一句话，必须指向具体可复用的技法"],
  "reusable": ["我能复用的：结构/钩子句式/话题配比/首图版式"],
  "not_reusable": ["不能复用的：依赖作者人设、特定时间节点、原创素材"],
  "risk": ["如果照着写，可能踩的坑"]
}
禁止笼统结论，例如「内容优质」「戳中痛点」这类不可执行的话一律不要。
```

### AI#3 仿写生成（核心）

```
用上面拆解出的【结构】和【标题句式】，写一篇全新的小红书笔记。
主题：<用户给的 topic>
行业背景：<你设定好的行业定位>

铁律：
1. 只借用结构和句式，禁止使用原文的任何完整句子
2. 所有案例、数字必须换成本主题的，拿不准就写 TODO: 不要编造
3. 正文 ≤ 1000 字，每段 ≤ 3 行

输出 JSON：
{
  "titles": ["5 个候选，≤20 字，带情绪钩子"],
  "body": "正文",
  "topics": ["8 个，按 大词2+中词3+长尾3 配"],
  "cover_text": {"main": "首图主标题 ≤12 字", "sub": "副标题 ≤18 字"},
  "cards": [{"h": "小标题", "p": "2-3 句话"}],
  "image_prompts": ["若走 AI 配图，每张一个提示词"]
}
```

### AI#4 首图文案（可选，单独优化）

首图决定点击率，值得单独跑一轮，让模型只产出 8 组封面文案候选并标注钩子类型。

## 5. 生图的三条路线

| 路线 | 做法 | 适合 | 代价 |
|---|---|---|---|
| **A. 文字卡**（推荐首选） | 把 `cover_text` + `cards` 套进 HTML 模板，Playwright 截图成 1242×1660 PNG | 干货、教程、清单类 | 零成本、风格统一、可控；需要做模板 |
| **B. AI 配图** | 即梦 / 可灵 / Gemini Image 等，用 `image_prompts` | 氛围、生活方式类 | 有成本；**必须按规定标识 AI 生成** |
| **C. 混合** | 首图用文字卡（保证信息传达），内页 AI 图 | 大多数账号 | 最佳折中 |

**首图强烈建议用文字卡**：小红书的点击率几乎全靠首图那几个字，AI 生图控不住文字，经常出鬼画符。
这里有个现成的复用点——`yilin-tools` 的 `lib/cards` 就是一套成熟的「文字 → 长图卡」引擎（解析、断行、分页、Canvas 绘制、模板配色都写好了），把它抽成一个 CLI 或在 bridge 里直接调，首图和内页卡片一次出完。

## 6. 风控（决定这个号能活多久）

| 规则 | 为什么 |
|---|---|
| **有头浏览器**（headful），不要 headless | 小红书对 headless 特征检测很成熟 |
| 复用真实 `user-data-dir`，不改 UA、不开代理 | 环境指纹突变 = 异常登录 |
| 每天发布上限 **1–3 条**，间隔随机 2–6 小时 | 固定节奏的高频发布是最明显的机器特征 |
| 填表单用 `type(..., {delay: 50~150})` 而不是直接 set value | 模拟人类输入 |
| 每一步之间随机 sleep 0.5–2 秒 | 同上 |
| 登录态失效 → **告警，不重试** | 反复失败触发风控 |
| 先用小号跑两周 | 代价最低的试错方式 |
| 保留 `autoConfirm=false` | 事故稿发不出去 |

**明确说一句**：这类自动化违反小红书用户协议，账号被限流或封禁的风险由你承担。我按你的要求给出完整设计，但 `autoConfirm` 默认关着——要不要打开那个开关，是你的决定，不是默认值。

## 7. 分三期落地

| 期 | 范围 | 你能得到什么 | 工作量 |
|---|---|---|---|
| **P0** | bridge 的 `/health` `/login` `/note/fetch` + 三个 AI 节点 + 写 Notion | 给个链接，10 秒出拆解报告和仿写稿，人工复制去发 | 1 天 |
| **P1** | 文字卡生图 + `/note/publish`（autoConfirm=false） | 图文全自动填好，你只点发布 | 2–3 天 |
| **P2** | 数据回收 + 周报 + 按数据调整仿写策略 | 流水线开始自我迭代 | 1–2 天 |

**不要跳过 P0 直接做 P2。** P0 跑两周之后你才知道：模型拆解得准不准、仿写稿要改多少、哪类参考链接根本不值得仿。这些认知会把 P1 的设计全改一遍。

## 8. 失败处理清单

| 故障 | 表现 | 处理 |
|---|---|---|
| 登录态过期 | `/health` 返回 `loggedIn:false` | 告警 → 你执行 `/login` 扫码 |
| 参考链接抓不到 | `/note/fetch` 超时或字段为空 | 大概率是笔记被删或需要登录；回退到「手动粘贴正文」分支 |
| 仿写重合度超标 | 查重节点 `pass:false` | 自动重写一次，再超标就转人工 |
| 发布页改版 | `/note/publish` 找不到选择器 | bridge 里选择器集中成一个常量表，改一处即可 |
| 图片上传失败 | 上传后图片数不符 | 重试 1 次，失败则保留草稿并告警 |
